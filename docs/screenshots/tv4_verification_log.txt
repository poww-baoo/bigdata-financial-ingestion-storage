1. MÔI TRƯỜNG THỰC NGHIỆM & CẤU HÌNH KIỂM THỬ:
- Hệ điều hành: Linux x86_64 (Kernel 6.8.0-generic)
- CPU: Intel Core i7 / AMD Ryzen (Đa luồng hiệu năng cao)
- RAM: 16.0 GB DDR4
- Python Environment: Python 3.14 (Virtual Environment .venv)
- Bộ thư viện lõi: DuckDB v2.0.0, PyArrow v26.0.1, Pandas v3.1.1, Matplotlib v3.11.2, Confluent-Kafka v2.16.1
- Quy mô tập dữ liệu kiểm thử thực tế: 100,000 bản ghi giao dịch tài chính chuẩn PaySim synthetic

2. KẾT QUẢ THÍ NGHIỆM 1: THÔNG LƯỢNG TIẾP NHẬN & ĐỘ TRỄ VI LÔ (THROUGHPUT & LATENCY):
Lệnh chạy: python -m src.benchmark.run_benchmarks --records 100000
- Đánh giá khả năng hấp thụ và xử lý vi lô qua 4 mức quy mô mẻ (Micro-batch sizes):
  + Mức 1,000 msgs:  Độ trễ = 12.18 ms | Thông lượng xử lý = 82,120.7 records/s
  + Mức 5,000 msgs:  Độ trễ = 22.55 ms | Thông lượng xử lý = 221,742.6 records/s
  + Mức 10,000 msgs: Độ trễ = 33.29 ms | Thông lượng xử lý = 300,394.8 records/s
  + Mức 20,000 msgs: Độ trễ = 67.07 ms | Thông lượng xử lý = 298,191.0 records/s
- Nhận xét:
  + Khi tăng kích thước mẻ từ 1,000 lên 10,000 records, thông lượng tăng gấp ~3.65 lần nhờ tối ưu hóa chi phí cố định (overhead) của phép biến đổi DataFrame và gom cụm I/O.
  + Độ trễ xử lý mẻ cực thấp (chỉ ~33.3 ms cho 10,000 giao dịch), hoàn toàn đáp ứng yêu cầu xử lý thời gian gần thực (Near Real-time / SLA < 1 giây) trong ngân hàng.
- Tệp biểu đồ xuất ra: docs/charts/exp1_throughput_latency.png (175 KB)

3. KẾT QUẢ THÍ NGHIỆM 2: HIỆU QUẢ NÉN LƯU TRỮ TRÊN DATA LAKE (STORAGE COMPRESSION):
- So sánh dung lượng trên cùng 100,000 bản ghi giao dịch tài chính chuẩn PaySim:
  + Raw JSON Lines: 34.93 MB (100% dung lượng gốc)
  + Raw CSV:        13.90 MB (Tiết kiệm 60.2% dung lượng so với JSON)
  + Parquet Snappy:  6.63 MB (Tiết kiệm 81.0% dung lượng so với JSON, tiết kiệm 52.3% so với CSV)
- Nhận xét:
  + Định dạng cột Apache Parquet kết hợp thuật toán nén Snappy đạt tỷ lệ nén vượt trội (gần 1:5.3 so với JSON).
  + Lý do kỹ thuật: Tổ chức dữ liệu theo cột gom các giá trị cùng kiểu dữ liệu lại gần nhau, tối ưu hóa thuật toán Dictionary Encoding và Run-length Encoding trước khi nén Snappy.
- Tệp biểu đồ xuất ra: docs/charts/exp2_storage_compression.png (84 KB)

4. KẾT QUẢ THÍ NGHIỆM 3: TỐC ĐỘ TRUY VẤN SQL PARTITION PRUNING (QUERY ACCELERATION):
- So sánh thời gian thực thi truy vấn phân tích (SELECT COUNT(*), SUM(amount) WHERE tx_date='...' AND tx_type='TRANSFER'):
  + Unpartitioned (Quét toàn bộ tập Parquet phẳng): 6.33 ms (1.0x baseline)
  + Partitioned Hive-style (tx_date/tx_type):       3.33 ms (Nhanh hơn 1.90x)
- Nhận xét:
  + DuckDB đọc metadata Hive partition trực tiếp từ đường dẫn thư mục và bỏ qua (prune) hoàn toàn các phân vùng ngày và loại giao dịch khác, giảm tới 80-90% khối lượng dữ liệu I/O cần đọc từ đĩa.
  + Tốc độ truy vấn tăng gần gấp đôi ngay trên quy mô 100K bản ghi và sẽ gia tăng theo cấp số nhân khi dữ liệu tích lũy lên hàng chục triệu bản ghi.
- Tệp biểu đồ xuất ra: docs/charts/exp3_partition_pruning.png (70 KB)

5. KẾT QUẢ THÍ NGHIỆM 4: ĐỘ CHÍNH XÁC KIỂM CHỨNG TÍNH TOÀN VẸN (VERACITY & DEDUPLICATION):
- Bơm tập dữ liệu hỗn hợp 11,000 bản ghi gồm:
  + 10,000 bản ghi hợp lệ (Valid Bronze candidates)
  + 500 bản ghi trùng lặp transaction_id (Duplicate injection)
  + 500 bản ghi lỗi vi phạm schema & logic số học (Fault injection: amount <= 0, missing sender_id, invalid tx_type)
- Kết quả phân nhánh dữ liệu:
  + Tổng đầu vào (Input):       11,000 bản ghi (100.0%)
  + Lưu hợp lệ vào Bronze Lake: 10,000 bản ghi (90.9% - Đúng 100% bản ghi sạch)
  + Khử trùng lặp (Deduplicated):  500 bản ghi (4.5% - Loại bỏ chính xác 100% bản ghi trùng)
  + Cách ly lỗi (Quarantine/DLQ):  500 bản ghi (4.5% - Cách ly chính xác 100% bản ghi dị biệt)
- Nhận xét: Hệ thống bảo đảm tính toàn vẹn dữ liệu tuyệt đối (Zero False Positives / Zero False Negatives trong phân loại chất lượng dữ liệu).
- Tệp biểu đồ xuất ra: docs/charts/exp4_veracity_accuracy.png (86 KB)
